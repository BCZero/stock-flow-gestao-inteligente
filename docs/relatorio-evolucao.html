1.Resumo

O StockFlow é um sistema web de gestão de estoque voltado a pequenos varejistas. Cada empresa-cliente opera em um ambiente logicamente isolado (arquitetura multi-tenant) e conta com um motor transacional que impede saldo negativo mesmo com vendas simultâneas, um histórico imutável de movimentações, uma trilha de auditoria e alertas automáticos de estoque crítico, produto parado, atraso de fornecedor e variação de vendas.

Este relatório descreve como o projeto evoluiu desde o primeiro commit (08/10/2026) até o estado atual, o que foi planejado e o que foi efetivamente entregue, as principais decisões de engenharia, as verificações executadas e as limitações que ainda existem. Todas as afirmações foram conferidas contra o código-fonte, o histórico do Git e uma execução da suíte de testes em 09/11/2026.

2.Contexto e problema

O projeto nasceu das oficinas de Laboratório de Inovação II, cujo desafio era conceber, modelar e implementar uma solução de software completa, integrando modelagem relacional com integridade rigorosa, controle de acesso por perfis, tecnologias web modernas e entrega incremental em seis fases. O ponto de partida foi um Projeto Lógico e Físico de Banco de Dados, um Plano de Negócios e um Project Model Canvas.

O problema atacado é recorrente no pequeno varejo: controles em planilhas, sem rastreabilidade (“quem alterou este saldo?”), vendas que superam o estoque físico, capital imobilizado em produtos parados e reação tardia a mudanças de demanda e a atrasos de fornecedores.

4.Arquitetura

O sistema segue uma arquitetura em três camadas: uma aplicação de página única (SPA) em React consome uma API REST em FastAPI, que persiste em PostgreSQL. Um monitor assíncrono, executado dentro do próprio processo da API, gera os alertas periodicamente; um provedor de LLM é opcional.

5.Decisões de engenharia em destaque

Isolamento multiempresa no banco

Toda tabela de domínio tem id_empresa e as relações usam chaves estrangeiras compostas (id_empresa, id). O PostgreSQL recusa (SQLSTATE 23503) vincular registros de empresas diferentes mesmo que o código da aplicação falhe. O token JWT carrega só o id do usuário; a empresa é lida do banco.

Saldo nunca negativo

Duas barreiras: a aplicação bloqueia as linhas de saldo (SELECT … FOR UPDATE) e recusa saldo posterior < 0; o banco tem CHECK (quantidade >= 0). Os bloqueios seguem ordem determinística (produto, local) para evitar deadlock.

Ledger e auditoria imutáveis

movimentacao_estoque guarda saldo anterior e posterior de cada operação, com CHECK que valida a aritmética. Um trigger bloqueia UPDATE e DELETE nesta tabela e em evento_auditoria. Produtos com histórico são desativados, nunca apagados.

Idempotência

Ajustes e recebimentos exigem uma chave UUID: reenviar a mesma requisição não duplica o estoque; reutilizar a chave com dados diferentes retorna 409. Confirmar uma venda já confirmada não baixa o estoque de novo.

Alertas sem duplicidade

Índice único parcial por condição ativa + bloqueio por empresa: dois processamentos simultâneos geram um alerta. Quando a condição normaliza o alerta se encerra sozinho; se o problema reaparecer, nasce um novo.

IA com degradação graciosa e privacidade

O LLM é opcional e recebe apenas referências temporárias e números — nunca nomes, e-mails ou IDs. Sem configuração, falha de rede ou resposta inválida, o painel usa as orientações das regras, sem erro para o usuário.

5.1. Ciclo de vida dos documentos

CompraRASCUNHO → confirmar → CONFIRMADA → receber (parcial) → PARCIAL → receber (restante) → RECEBIDA. Somente o recebimento altera o saldo.
VendaRASCUNHO → confirmar → CONFIRMADA. A baixa de todos os itens ocorre numa única transação; se um item faltar, nada é baixado e a venda segue em rascunho.
AlertaNOVO → LIDO → EM_TRATAMENTO → RESOLVIDO | DESCARTADO (encerrar exige justificativa).

7.2. Dados de demonstração

O script popular_demo.py cria duas lojas fictícias com 90 dias de operações e cenários determinísticos (estoque crítico, produto parado há 75 dias, queda de 30 % nas vendas, produto sem base anterior, fornecedor em atraso e o mesmo SKU em empresas distintas). A carga é idempotente e serve para apresentações e para exercitar os alertas.

8.Estado atual e limitações conhecidas

Estado: o sistema está operacional e demonstrável: login com 2FA, painel, cadastros, estoque, compras, vendas, alertas, notificações, auditoria e resumo por LLM funcionam de ponta a ponta. A Fase 6 está parcial.

Na revisão do código foram identificadas as limitações abaixo. Nenhuma impede a demonstração acadêmica; todas devem ser tratadas antes de qualquer uso em produção.

#LimitaçãoCorreção sugerida
1SECRET_KEY tem valor padrão fixo no código.Exigir a chave por ambiente e falhar ao iniciar se ausente.
2CORS aberto (allow_origins=["*"]) com credenciais.Restringir à origem do frontend.
3Login por nome usa .first(), mas o nome de usuário não é único.Tornar o nome único ou aceitar só e-mail.
4Cadastros (categorias, produtos, locais, pessoas) não verificam o perfil: um ANALISTA pode criar e excluir.Reutilizar as dependências de perfil do módulo de estoque.
5O frontend não oculta ações por perfil; só o backend bloqueia (403).Esconder ou desabilitar ações conforme o perfil.
6CPF/CNPJ não são validados.Validar dígitos verificadores no esquema Pydantic.
7Token em localStorage, sem refresh token.Cookie HttpOnly + refresh.
8Sem teste de volume, sem testes do frontend, sem CI.Concluir a Fase 6 e criar pipeline com Postgres de serviço.
